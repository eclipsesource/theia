## Investigated failures and remaining deviations

### Extension webview and embedded-content authority

- **Expected:** An installed extension opens a webview, runs its script, receives local resource content and messages back to its Node plugin host, then survives an HTML update.
- **Original failure:** The default `<uuid>.webview.127.0.0.1:<port>` host did not resolve locally. The authenticated backend also refuses alternate hosts, as intended. An early isolated endpoint experiment appeared to coincide with startup stalls; tracing later showed a separate native watcher failure.
- **Response:** The Tauri `plugin-ext` backend module serves only `/webview` bootstrap assets on IPv6 loopback `::1`, using `{{uuid}}.webview.localhost:<port>`. The controller supplies the fixed port in the endpoint pattern. The trusted backend remains on `127.0.0.1`, and its per-launch cookie is HTTP-only for that host.
- **Verification:** With a trusted disposable profile, invoke `tauriProbe.openWebview`. The plugin log contains `TAURI_PROBE_MESSAGE` for `ready`, `service-worker: ready` and `resource` at stages 1, 2 and 3, including expected text from `resource.txt`. Stage 2 updates HTML; stage 3 disposes and recreates the panel. All three stages attempted `ws://127.0.0.1:<port>/tauri-services` from the actual iframe and received close code 1006 after the handshake was refused. The separate static endpoint returned HTTP 200 for `/webview/index.html` and 404 for a dynamic service path; unauthenticated primary HTTP returned 403. After `view.reload`, log `/tmp/tauri-webview135.log` showed `TAURI_PROBE_RESTORED 3`, followed by ready/resource/service-worker and rejected WebSocket messages. After closing and relaunching the same profile, `/tmp/tauri-webview136.log` showed the same restoration and checks.
- **Remaining scope:** Custom editors, notebooks and mini-browser are not verified. The negative WebSocket result narrows the authority risk but does not prove the entire boundary. A native top-level navigation guard rejected `http://localhost:30551/webview/index.html` while permitting the trusted backend and extension webview origins. Other navigation and iframe authority paths remain unverified.

### Repeat launch stall

- **Expected:** Each launch reaches frontend `ready` and the Node backend continues serving requests.
- **Actual before fix:** Multiple launches stopped with a listening backend socket that timed out on HTTP. The main Node thread waited in a futex. `strace -f` showed a missing `watchman` executable returning 127, then later an `inotify_init1(IN_NONBLOCK|IN_CLOEXEC) = -1 EMFILE` call in a native watcher startup thread. The latter thread exited before `@parcel/watcher` signaled startup, leaving the main thread blocked. This session's per-user inotify instance limit is 128; a process scan found more than 128 inotify descriptors held by the user. The missing `watchman` probe was incidental, not the final wait point.
- **Response:** The two AI registry directory watches use `@parcel/watcher` snapshot operations on a one-second timer for the Tauri Linux target. Its native `brute-force` backend supports snapshots but not subscriptions; a direct subscription attempt aborted and was removed. Electron and browser retain their previous watcher route. The snapshot helper delivered a create event in a standalone check.
- **Verification and limit:** Three consecutive launches of the same disposable profile with the probe plugin reached frontend `ready` after this change. The integrated terminal then executed a shell command in another launch. This is a targeted mitigation under a resource-exhausted session, not proof of long-running reliability or every watcher under the same limit. Native filesystem watching in its separate process and arbitrary crash cleanup remain to be checked.

### Real-display animation frame stall

- **Expected:** The frontend leaves its loading indicator and reaches `ready` on the available X11 display.
- **Actual before fix:** Two short real-display launches stopped after the `started_contributions` state. Source inspection showed the next startup step waits for `requestAnimationFrame` after attaching the shell. On a stalled page, `document.visibilityState` was `visible`, a 100 ms timer fired, but an explicitly scheduled animation frame remained pending. The stalled window showed the loading spinner. The first real-display launch had reached `ready`, so this was intermittent rather than universal.
- **Response:** `FrontendApplication` now waits at most 500 ms at its two startup animation-frame points before continuing. The normal animation-frame path still wins when frames run. This is a shared frontend fix for browsers that throttle or withhold frames at startup.
- **Verification:** The previously stalled real-display profile reached `attached_shell` and `ready` after the change, then closed cleanly. The browser example rebuilt and served HTTP 200. The Electron example rebuilt and reached frontend `ready` under Xvfb. The Tauri bundle rebuilt after switching native dependencies back; Node 24 loaded `node-pty`, `keytar` and `native-keymap`. Extended real-display use is still untested.

### Mini-browser local content

- **Expected:** A local HTML or other supported file opens in the mini-browser iframe on an origin separate from the trusted frontend.
- **Current failure:** The generic frontend builds `{{uuid}}.mini-browser.{{hostname}}`. With Tauri's trusted hostname `127.0.0.1:<port>`, `getent ahosts test.mini-browser.127.0.0.1` failed on this machine. `test.mini-browser.localhost` resolves to loopback, but the Tauri `::1` server currently serves only static extension webview assets and does not expose mini-browser file content.
- **Security constraint:** The generic mini-browser endpoint can serve file paths selected from the request URL. Simply adding that route to the unauthenticated `::1` static server would let other local users read files available to the Theia process. A separate authenticated content route or scoped capability is needed. This feature is unresolved; a DNS change alone is not a safe fix.

## 2026-09-26 follow-up: remote architecture and concurrent launches

The remote and dev-container Electron manifest entries cannot be used as Tauri aliases. The existing remote setup copies the current application's `lib/backend/main.js` and starts it on the remote machine without a native host. The Tauri host also limits top-level navigation to the window's own backend port; the local backend currently accepts service requests only from that exact origin. ## 2026-09-27 follow-up: serialized native-module preparation

The shared application-manager rebuild path previously checked `.browser_modules` before any coordination, so simultaneous Electron and standalone-Node preparations could act on the same cache state. It now takes an atomic `.browser_modules.lock` directory under the configured cache root before inspecting the cache, backing up modules, rebuilding for Electron, or restoring standalone modules. A second preparer waits while the owner PID is alive. A lock left by an exited process, or an incomplete lock with no owner record, yields a clear recovery error rather than modifying the shared modules. The lock is removed in `finally`; running application processes still have to be stopped before an ABI switch.

The helper's two tests passed: a second holder waited until the first released, and a dead-owner lock produced the stale-lock error. `@theia/application-manager` compile and targeted ESLint passed. A full Electron rebuild processed `keytar`, `drivelist`, `native-keymap` and `node-pty`; a subsequent Tauri rebuild restored them and Node 24 loaded `node-pty`, `native-keymap` and `keytar`. In a separate contention check, Tauri preparation started while Electron held the lock, waited, and then restored the standalone modules. Both processes exited successfully, `.browser_modules` and `.browser_modules.lock` were absent afterward, and the same addon load check passed. This tests two local preparers; SIGKILL leaves a lock for manual recovery, and it does not isolate native modules from already-running processes.
